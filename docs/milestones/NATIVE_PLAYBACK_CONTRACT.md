# Native playback device boundary, revision 1

7 November 2026. This boundary adds deliberate native-device playback of the existing immutable M2 audio plan. It does not replace the finite voice renderer, approve a timbre, introduce live synthesis, or qualify a complete instrument. The existing M2 equations, deterministic admission, eight primary/eight retirement states, tails and transport transitions remain authoritative.

## Public control and ownership

`atlas/playback.hpp` is portable C++20, with no JUCE types. One serial control worker owns `PlaybackRuntime`, calls `prepare`, `enable`, `command`, `snapshot`, `heartbeat` and `service`, and destroys it. These calls are not safe between multiple control threads. `OutputDriver` is injected; hardware-free tests implement the same interface and invoke the actual `process` entry point. Its `stop` must flush pending callbacks before returning, including partially started devices.

The runtime owns one immutable `AudioPlan`, one borrowing `AudioRenderer`, a fixed 8,192-float scratch buffer, scalar lock-free atomics and a one-entry command mailbox. Preparing first stops output and panics the old renderer on the control worker. New plan compilation/construction occurs while quiescent. The old renderer is destroyed before its old plan. Construction failure leaves output disabled and never restores playback. Successful preparation assigns a new monotonically increasing numeric preparation ID; JSON adapters may render it as an opaque string. Renderer generations remain distinct from preparation IDs and increment on stop, panic, seek and device invalidation. IDs and generations must be matched together.

Output starts disabled. `enable(true)` requires preparation, opens the current default output and starts silent callbacks. It never calls play, reconstructs tails, restarts after failure or selects a substitute format. Preparing always disables output. Enable, seek, stop and panic can change the generation, so clients use the returned actual snapshot for subsequent controls. The default plan uses 48 kHz, MIDI root 60, 8 ms attack, 650 ms decay and -18 dB master attenuation. Gain is immutable per prepared plan; no runtime gain automation is advertised.

## Commands and callback

A command includes kind, preparation ID, expected generation and seek frame. Normal commands reject stale IDs/generations before publication and again before execution. Stop/panic with both identifiers zero are unconditional, idempotent safety operations, succeeding even before preparation. Play/pause require enabled output; stop, seek and panic also work quiescent while disabled. The existing renderer decides legal transitions and frame limits.

The control worker releases one mailbox request sequence and waits off audio for an acknowledgement for at most 250 ms. The callback acquires the sequence, copies/applies the command, renders, publishes position/generation/state, then releases the acknowledgement. The control worker cannot publish another command until the previous call completes; no queue overflow can discard a release/panic behind ordinary commands. Acknowledgement failure or stalled callbacks close the device, establish quiescence and panic before reporting `command_timeout`. This is command completion, not acceptance into an unobserved queue. A rejected renderer transition reports `invalid_transition`.

One callback consumes the mailbox and borrows the stable renderer. It clears supplied output channels, validates stereo pointers and frame count, applies at most one command, invokes the existing renderer once and copies stereo scratch into output channels 0/1. Spare channels remain zero. Zero frames are a no-op. Unsupported/missing buffers or blocks above 4,096 frames are silenced and latch `callback_failure`; the callback never subdivides an unsupported hardware block to hide a format error. The driver must supply valid extents for every channel/frame it reports, with hard limits of 64 channels and 65,536 frames. Rejected blocks of 4,097–65,536 frames are fully cleared. Counts beyond those driver limits are contract violations; clearing is capped at those hard limits rather than trusting arbitrary integers or unknown memory. Renderer work is capped at 4,096 frames and 16 voice states. No plan ownership, allocation/free, locks, waits, exceptions, JSON, database, logging, clock query or UI work occurs in this application callback.

Position/generation/state are published under an atomic sequence counter with atomic payload fields. Only the worker retries reads; the callback never waits for a reader. A callback suspended during publication can delay that worker snapshot read until the callback progresses; no realtime thread waits on this read. Preparation metadata is worker-owned and stable during callbacks. Compile-time assertions require the scalar atomic types used on the callback to be lock-free. This is not a claim that the operating system or JUCE backend has no internal synchronization.

## Device transitions and failures

Driver start must call `deviceStarted` before processing. Exact prepared sample rate, 2–64 supplied output channels and a nonzero block at most 4,096 frames are required. A second start notification invalidates the device instead of silently resuming the prepared timeline. Runtime callback errors, unexpected stops, device errors, selected-device removal and default-output changes latch an observable typed failure and silence later callbacks. The worker's next service call closes and panics. Explicit user enable is required after failure; no automatic playback resumes.

The JUCE adapter discovers the current default device using `AudioDeviceManager` only for device-type enumeration. It opens and starts a direct `AudioIODevice` with no inputs and the first two output channels; AudioDeviceManager is absent from the signal callback path. All discovery/open/start/stop/destruction executes on JUCE's main message thread; the stdin control worker waits off audio for these lifecycle actions. JUCE documents that `AudioIODevice::stop()` flushes pending callback calls before returning. We rely on that guarantee before clearing the non-owning runtime pointer or retiring any renderer/plan. Device-list notifications are checked on the message thread against the chosen default-output name: disappearance or a changed default invalidates playback. Unrelated list changes are ignored. JUCE CoreAudio itself creates a private aggregate device during open, which emits such a notification without changing our selected default. Actual format changes/unexpected stops still invalidate through the device lifecycle callbacks. No default-device migration or resampling is implemented.

## Listening lease and process lifetime

`getTransport` calls `heartbeat`, which only refreshes an existing listening lease. It cannot enable sound. The worker calls `service` every 100 ms when idle; five seconds without a heartbeat closes output. A clock-free callback countdown independently permits at most five seconds of processed audio frames between observed heartbeat serial changes, including ready/paused silent callback time. Crossing the bound hard-panics and silences the whole crossing block, then latches `lease_expired`. This intentionally differs from exact wall time by at most a callback block; callback time cannot detect an entirely stalled device, so worker wall time handles that case. The callback fallback protects output when the worker is temporarily blocked in verification/SQLite. Re-enable requires a deliberate action and does not auto-play.

`atlas-audio-host version` reports the generated source identity before JUCE initialization or device discovery. `atlas-audio-host ui-host --db PATH` uses public `JUCEApplicationBase::main` and a `JUCEApplicationBase` subclass to initialize and run the native application/message loop on the main thread and one serial stdin worker. Unix/macOS stdin uses 100 ms poll and raw reads, processes newline-delimited JSON, bounds each request at 16 KiB and bounds excess-line accumulation. EOF closes the device and destroys host/runtime before ending the message loop. The host entry point explicitly requires POSIX bounded stdin polling; non-POSIX builds need a proper bounded platform input-wait adapter. The portable runtime remains independent of this host restriction. No owner database writes, collector control or provider requests are part of this process.

## Confirmed macOS host regression and correction

The first real-host smoke on 7 November found a lifecycle deadlock before audio enable. A read-only one-second sample of the never-enabled disposable host showed the main thread already in `std::thread::join`, with the stdin worker waiting in JUCE `callFunctionOnMessageThread` from `enable(false)`. At the installed JUCE9 pin, `ScopedJuceInitialiser_GUI` initializes `MessageManager` but does not create `NSApplication`; the raw macOS dispatch loop therefore returned immediately. The public `JUCEApplicationBase::main(argc, argv)` path creates `NSApplication` before the event loop. The host now uses that public application lifecycle, keeps its message loop alive until the worker has destroyed runtime/driver, and only then posts quit and joins during shutdown. OS quit requests ask the 100 ms poll worker to finish while message dispatch remains alive. A `--prepare-only` mode in the explicit device-smoke script exercises this exact actual-host preparation/shutdown path without opening a device, as a hardware-free regression.


The second real-device attempt successfully opened stereo 48 kHz at -18 dB, then exposed a separate listener-policy defect: JUCE9 CoreAudio creates its own private aggregate device while opening output, and its device type emits a delayed device-list notification for that aggregate. Invalidating on every list notification therefore stopped our unchanged default before the first play command. The corrected listener compares chosen/default output names and invalidates only disappearance or default change, leaving actual format/stop/error callbacks authoritative. At this installed pin CoreAudio type invokes these listeners from `AsyncUpdater::handleAsyncUpdate`, so the name/default lookup stays on the message thread and outside audio processing. The pre-fix device receipt is preserved separately; no automatic retry or vendor-code modification was used.

After both corrections, the bounded actual default-output smoke passed in 2.237 seconds on macOS 15.6.1 arm64. The immutable executable SHA256 was `25ee4e92c82c428f9ccebb45e662701d2e39ad6a2e439d0f4ca5502921cd401e`, reporting source identity `8e28e07b0e0a149df57c41b56be185c8c4eeeead6064c08a4871757c47636826`. A disposable, verified three-second demo session held notes at 0, 0.3 and 0.6 seconds. At 48 kHz/-18 dB the device remained silent after enable, then callback position advanced under explicit play, pause settled/froze, paused seek changed generation, resume advanced, stop reset position, disable succeeded, and EOF exited 0 without forced termination. The temporary database filename contained spaces and its hash stayed unchanged. Full request/reply and cleanup receipts are in `evidence/native-playback/device-smoke.json`; both failed pre-fix receipts are retained. This establishes one brief real-device callback/transport smoke only: no microphone, heard-audio judgment, physical-speaker routing, latency, CPU, DAW or sustained-device qualification is claimed.


## Deliberate output configuration, revision 2

The serial control worker owns the portable catalog, configuration and control revision. The optional driver catalog defaults to unavailable. A JUCE catalog enumerates metadata on the message thread without opening a device: at most 128 outputs and 64 rates/buffer sizes per output, bounded strings and opaque stable IDs derived from type/name. Duplicate names or ID collisions are rejected rather than selecting an ambiguous output. This name-based identity cannot track renamed hardware.

`getAudioDevices({})` refreshes metadata and returns `available`, `devices`, `configuration`, `active`, decimal-string `controlRevision`, `error`, and preparation/generation identity. Configuration is `{mode:systemDefault|explicitDevice,deviceId:null|catalogId,bufferFrames:0|supportedSize}`; zero selects the device default buffer. Active metadata is null while disabled and otherwise reports the actual opened device/format. Entries contain id/name/type/default flag/output count, rates, buffer sizes and default buffer. Discovery never enables or plays output. Catalog changes increment control revision.

`setAudioDevice({controlRevision,preparationId,generation,configuration})` refreshes first, rejects stale catalog/playback identities, unknown IDs, unsupported stereo/rate/buffer selections and malformed/bounded arguments before changing a running device. Accepted configuration stops output, establishes callback quiescence, panics the renderer, increments control revision and leaves Listening disabled. The returned catalog carries the resulting generation. Explicit Listening and Play are required. Explicit selections never fall back; default mode resolves only on explicit enable. Device removal/default change faults and silences with no migration/restart. A restored syntactically valid disconnected preference stays selected and fails on enable. Persistence belongs to the standalone adapter and never restores enable/play state.

Numeric lifetime callback/frame/latched-fault counters use lock-free scalar atomics. Actual rate/buffer/channel counts are published numerically at start and cleared after quiescence. Strings stay on worker/message threads; callback and noexcept snapshot publication never allocate or copy strings. Audio polling uses cached metadata instead of rescanning hardware.

Verification covers invalid/stale configuration, disconnected restored selection, rate/buffer enforcement, quiet reconfiguration/recovery, catalog revision invalidation, cumulative counters, repeated fault/recovery epochs and callback allocation/free guards. Synthetic sustained frame processing is separate from elapsed-time physical-device qualification.
