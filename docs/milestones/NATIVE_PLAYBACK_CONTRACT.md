# Native playback device boundary, revision 1

7 November 2026. This boundary adds deliberate native-device playback of the existing immutable M2 audio plan. It does not replace the finite voice renderer, approve a timbre, introduce live synthesis, or qualify a complete instrument. The existing M2 equations, deterministic admission, eight primary/eight retirement states, tails and transport transitions remain authoritative.

## Public control and ownership

`atlas/playback.hpp` is portable C++20, with no JUCE types. One serial control worker owns `PlaybackRuntime`, calls `prepare`, `enable`, `command`, `snapshot`, `heartbeat` and `service`, and destroys it. These calls are not safe between multiple control threads. `OutputDriver` is injected; hardware-free tests implement the same interface and invoke the actual `process` entry point. Its `stop` must flush pending callbacks before returning, including partially started devices.

The runtime owns one immutable `AudioPlan`, one borrowing `AudioRenderer`, a fixed 8,192-float scratch buffer, scalar lock-free atomics and a one-entry command mailbox. Preparing first stops output and panics the old renderer on the control worker. New plan compilation/construction occurs while quiescent. The old renderer is destroyed before its old plan. Construction failure leaves output disabled and never restores playback. Successful preparation assigns a new monotonically increasing numeric preparation ID; JSON adapters may render it as an opaque string. Renderer generations remain distinct from preparation IDs and increment on stop, panic, seek and device invalidation. IDs and generations must be matched together.

Output starts disabled. `enable(true)` requires preparation, opens the current default output and starts silent callbacks. It never calls play, reconstructs tails, restarts after failure or selects a substitute format. Preparing always disables output. Enable, seek, stop and panic can change the generation, so clients use the returned actual snapshot for subsequent controls. The default plan uses 48 kHz, MIDI root 60, 8 ms attack, 650 ms decay and -18 dB master attenuation. Gain is immutable per prepared plan; no runtime gain automation is advertised.

## Commands and callback

A command includes kind, preparation ID, expected generation and seek frame. Normal commands reject stale IDs/generations before publication and again before execution. Stop/panic with both identifiers zero are unconditional, idempotent safety operations, succeeding even before preparation. Play/pause require enabled output; stop, seek and panic also work quiescent while disabled. The existing renderer decides legal transitions and frame limits.

The control worker releases one mailbox request sequence and waits off audio for an acknowledgement for at most 250 ms. The callback acquires the sequence, copies/applies the command, renders, publishes position/generation/state, then releases the acknowledgement. The control worker cannot publish another command until the previous call completes; no queue overflow can discard a release/panic behind ordinary commands. Acknowledgement failure or stalled callbacks close the device, establish quiescence and panic before reporting `command_timeout`. This is command completion, not acceptance into an unobserved queue. A rejected renderer transition reports `invalid_transition`.

One callback consumes the mailbox and borrows the stable renderer. It clears supplied output channels, validates stereo pointers and frame count, applies at most one command, invokes the existing renderer once and copies stereo scratch into output channels 0/1. Spare channels remain zero. Zero frames are a no-op. Unsupported/missing buffers or blocks above 4,096 frames are silenced and latch `callback_failure`; the callback never subdivides an unsupported hardware block to hide a format error. The driver must supply valid extents for every channel/frame it reports, with hard limits of 64 channels and 65,536 frames. Rejected blocks of 4,097–65,536 frames are fully cleared. Counts beyond those driver limits are contract violations; clearing is capped at those hard limits rather than trusting arbitrary integers or unknown memory. Renderer work is capped at 4,096 frames and 16 voice states. No plan ownership, allocation/free, locks, waits, exceptions, JSON, database, logging, clock query or UI work occurs in this application callback.

Position/generation/state are published under an atomic sequence counter with atomic payload fields. Only the worker retries reads; the callback never waits for a reader. A callback suspended during publication can delay that worker snapshot read until the callback progresses; no realtime thread waits on this read. Preparation metadata is worker-owned and stable during callbacks. Compile-time assertions require the scalar atomic types used on the callback to be lock-free. This is not a claim that the operating system or JUCE backend has no internal synchronization.

## Device transitions and failures

Driver start must call `deviceStarted` before processing. Exact prepared sample rate, 2–64 supplied output channels and a nonzero block at most 4,096 frames are required. A second start notification invalidates the device instead of silently resuming the prepared timeline. Runtime callback errors, unexpected stops, device errors and device-list changes latch an observable typed failure and silence later callbacks. The worker's next service call closes and panics. Explicit user enable is required after failure; no automatic playback resumes.

The JUCE adapter discovers the current default device using `AudioDeviceManager` only for device-type enumeration. It opens and starts a direct `AudioIODevice` with no inputs and the first two output channels; AudioDeviceManager is absent from the signal callback path. All discovery/open/start/stop/destruction executes on JUCE's main message thread; the stdin control worker waits off audio for these lifecycle actions. JUCE documents that `AudioIODevice::stop()` flushes pending callback calls before returning. We rely on that guarantee before clearing the non-owning runtime pointer or retiring any renderer/plan. Device-list changes conservatively invalidate playback, even when the changed device is unrelated. No default-device migration or resampling is implemented.

## Listening lease and process lifetime

`getTransport` calls `heartbeat`, which only refreshes an existing listening lease. It cannot enable sound. The worker calls `service` every 100 ms when idle; five seconds without a heartbeat closes output. A clock-free callback countdown independently permits at most five seconds of processed audio frames between observed heartbeat serial changes, including ready/paused silent callback time. Crossing the bound hard-panics and silences the whole crossing block, then latches `lease_expired`. This intentionally differs from exact wall time by at most a callback block; callback time cannot detect an entirely stalled device, so worker wall time handles that case. The callback fallback protects output when the worker is temporarily blocked in verification/SQLite. Re-enable requires a deliberate action and does not auto-play.

`atlas-audio-host version` reports the generated source identity before JUCE initialization or device discovery. `atlas-audio-host ui-host --db PATH` runs the JUCE message loop on the main thread and one serial stdin worker. Unix/macOS stdin uses 100 ms poll and raw reads, processes newline-delimited JSON, bounds each request at 16 KiB and bounds excess-line accumulation. EOF closes the device and destroys host/runtime before ending the message loop. The host entry point explicitly requires POSIX bounded stdin polling; non-POSIX builds need a proper bounded platform input-wait adapter. The portable runtime remains independent of this host restriction. No owner database writes, collector control or provider requests are part of this process.
